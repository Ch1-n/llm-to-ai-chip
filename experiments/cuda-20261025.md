# RTX 4090 D 上的教学模型 CUDA 检查

日期：2026-10-25。原始结果：[JSON](../data/llm-inference/cuda-rtx4090d-20261025.json)。测试脚本：[validate_cuda_notebook.py](../tools/validate_cuda_notebook.py)。

## 环境与模型

- NVIDIA GeForce RTX 4090 D，设备总显存 25250627584 字节，驱动 580.105.08。
- Python 3.12.3，PyTorch 2.7.0+cu128，CUDA Runtime 12.8，关闭 TF32，PyTorch CPU 线程数 4。
- 6 层，H=768，12 个 head，d=64，SwiGLU I=2048，词表 50257，最大上下文 512。
- 不共享输入 Embedding 与 LM Head；119690496 参数。
- 数据为随机权重与合成 token，没有读取训练数据，没有验证语言质量或收敛性。

脚本只提取 Notebook 中指定的模型定义，不运行数据集、训练主循环或保存 checkpoint 的单元格。输入指纹见 JSON 的 `notebook_sha256`，不能以原项目基线 commit 代替本地修改版。

## 原实现的问题和测试中的调整

原始 RoPE 的 rotate_half 按相邻通道配对，cos/sin 却用 repeat 排列。单位基向量在位置 1 旋转后的范数误差约 0.1303，不满足纯旋转的保范数性质。测试在内存中改为 repeat_interleave；没有改动原 Notebook 或服务器环境。

GPTConfig 的 head_size 是定义类时计算的默认值，修改 n_embd/n_head 不会自动更新。小配置显式传入 head_size=8；默认完整配置的 768/12=64 不受这个问题影响。

generate 仍有以下观察：请求生成 0 个 token 时会做 Prefill；请求 1 个 token 时还会多做一次 Decode；达到 block_size 后停止，超过 block_size 的 prompt 被截断。这些没有在原文件里修复。基准直接调用 forward，不把它称为完整生成 API 测试。

## 数值检查

小配置使用 3 层、H=24、3 head、d=8、词表 97、上下文 32、B=2。修正后独立 RoPE 基向量与范数测试通过；逐 token、5/1/7/19 分块及完整 Prefill 一致，各层各 head 的 K/V 形状和数值一致。改变后半段输入不影响前半段 logits，超长缓存加输入会抛出 ValueError。

完整配置比较长度 512 的完整前向与前 511 个位置 Prefill 加一步 Decode，检查最后一个位置的全部词表 logits：

| 精度 | 缓存对完整前向最大绝对误差 | 相对 L2 误差 |
| --- | --- | --- |
| FP32 | 2.5034e-6 | 1.0262e-6 |
| BF16 | 0.0239258 | 0.0105256 |
| FP16 | 0.00366211 | 0.00130026 |

FP32 断言 atol=3e-5、rtol=3e-4；BF16 使用 0.08/0.08，FP16 使用 0.01/0.01。低精度通过的是已声明容差的检查，不是 bitwise 等价。容差不能替代算子数学性质的独立验证，当前样例也不是所有输入的误差上界。

## 推理计时

推理权重直接转为指定 dtype，eval 加 inference_mode，不使用 autocast。每组预热 3 次、计时 20 次；每次等待 CUDA 完成，报告包含 Python 发起开销的墙钟时间。另存 CUDA Event 时间，但 Event 跨度也可能包含 kernel 之间的发起空隙，不能把它直接当作纯 kernel 执行时间。

共 24 组：3 个 dtype，B=1/12，Prefill S=128/512，Decode 的总可见 KV 长度=129/512。Decode 每次从固定历史缓存追加一个位置，不是连续增长的生成过程；缓存建立不计时，也不包含分词、采样、网络和请求排队。B=12 的输入复制自同一序列，不模拟真实服务请求的长度差异。

实现保留逐 head Python 循环、显式 Attention 分数、动态 torch.cat 缓存。Prefill 计算全部位置的 LM Head logits，Decode 只计算新增位置。未使用 SDPA、FlashAttention、torch.compile 或 CUDA Graph。

以下均为 S=512 或总可见 KV=512 时的墙钟时间中位数：

| 精度与 batch | Prefill ms | Decode ms |
| --- | --- | --- |
| FP32 B=1 | 40.653 | 34.420 |
| BF16 B=1 | 42.506 | 34.135 |
| FP16 B=1 | 41.185 | 34.367 |
| FP32 B=12 | 53.582 | 35.699 |
| BF16 B=12 | 45.368 | 39.792 |
| FP16 B=12 | 45.850 | 36.969 |

测量有波动，不能仅凭小差异排序。每组的 P10/P90 和其他形状见 JSON。不能把上述时间当作硬件上限，也不能据此推论 BF16 的一般性能。尚未通过 profiler 确定 CPU 发起、kernel 计算、缓存复制和分配的耗时占比。

## 显存

记录 PyTorch peak allocated 和 peak reserved，同时保存每组开始时的 allocated 与增量峰值。Decode baseline 包含已建立的历史缓存，测量峰值还可能包含新旧缓存暂时共存。数据不等于 nvidia-smi 总设备占用，也不等于 KV 理论容量。

以 BF16 为例：B=1、S=512 的 Prefill peak allocated 约 336.15 MiB；B=12 时约 991.57 MiB。包含模型权重、注册的 mask/RoPE buffer、激活、完整位置 logits 和临时张量。各进程阶段的存活张量会影响 baseline，跨行差值不能直接解释为某一算子的精确内存。

## 训练冒烟

每种精度使用相同随机种子构建新模型，B=12、S=512，dropout=0.1，AdamW lr=3e-4，固定合成 batch 运行 3 步。FP32 正常训练；BF16/FP16 使用 FP32 权重加 AMP，FP16 开启 GradScaler。每步检查 loss 和全部现存参数梯度有限，然后执行更新。

| 模式 | 三步 loss | Peak allocated GiB |
| --- | --- | --- |
| FP32 | 10.9855 → 10.5420 → 10.1490 | 10.244 |
| BF16 AMP | 10.9904 → 10.5336 → 10.1423 | 9.862 |
| FP16 AMP | 10.9904 → 10.5334 → 10.1422 | 9.849 |

这是执行链路检查，不是语言训练或收敛实验。精度间 dropout/RNG 行为可能不同，不要求这三条 loss 曲线严格相同。

## 复现

自行提供具有对应 SHA256 的本地 Notebook，使用具备 CUDA 的 PyTorch 环境：

```bash
python tools/validate_cuda_notebook.py /path/to/build_gpt.ipynb \
  --output /path/to/cuda-results.json --repeats 20
```

脚本执行指定的 Python 定义，只应对可信 Notebook 使用。模型定义和训练素材未随本仓库分发，来源说明见 [SOURCES](../SOURCES.md)。
