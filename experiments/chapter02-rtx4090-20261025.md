# 第二篇实验记录 RTX 4090

本轮在 2026 年 10 月 25 日完成。服务器实际提供的是 RTX 4090 24GB，不是 H20，也不是第一篇的 RTX 4090 D。下面只比较本轮同卡实验，不将跨机器的耗时变化归因于软件优化。

## 环境与完成范围

- 驱动 580.105.08，PyTorch 2.7.0+cu128，CUDA Runtime/Toolkit 12.8。
- 独立 venv 继承服务器现有 PyTorch；新增依赖安装在该环境，没有升级基础 PyTorch。
- 独立 FA2 为 `flash-attn==2.8.3`，PyTorch 的 `sdpa-flash` 单独记为另一个后端。
- FA3 由于显卡不是 Hopper，明确记为不可用。
- 首轮在 PyTorch 2.7 中安装了 FA4 `4.0.0b36` 和 CuTe DSL 4.8.1，但导入时缺少 `torch.float4_e2m1fn_x2`，首轮没有 FA4 性能数据。后续复用了服务器已有的 PyTorch 2.8 环境，前向测试通过，反向仍有架构限制，详见下节。
- 169 个整模型计时 case、15 个 Attention 微基准 case 完成；另有训练步骤计时和 GPU Profiler 时间线。
- 主检查共 62 条记录，其中 48 条通过、14 条不可用，包含算子输出/梯度和 FP32 模型检查。后补的 BF16 整模型检查存在 MoE 路由敏感性，不能把主检查通过解读成所有低精度端到端路径都通过。

原始样本、中位数、P10/P90、显存、环境与源码指纹汇总在 [结果数据](../data/chapter02/rtx4090-20261025.json)。原始 trace、日志、运行命令和源码快照保留在本地 `runs/rtx4090-20261025/`，不随仓库上传。主基准源码快照由上传包和未修改文件重建，已逐文件核对主实验环境记录的 SHA256，归档名为 `source-measured.tar.gz`，其 SHA256 为 `4b17dcbbf105a33d6546bfa5f08e41cee38a09c78ae3ecf7253a8235b902db25`。后续精度诊断有独立的环境与源码指纹，不覆盖原始性能结果。

## 测量口径

Dense 模型是 6 层、隐藏维 768、12 heads、FFN 中间维 2048、词表 50257，共 119,690,496 参数。推理权重为 BF16，关闭 dropout，只计算最后一个位置的 LM Head。训练步骤则使用 FP32 权重/AdamW 与 BF16 AMP，计算全部位置的 logits。

性能计时不启用 Profiler，每个推理 case 预热 5 次、计时 20 次，显式等待 CUDA 完成。下面是同步墙钟中位数，包含 Python 发起、内存操作与计算的整体开销。没有锁定 GPU 频率，不以单次小差异作普遍结论。

默认比较静态缓存。Prefill 包含新缓存分配和写入；Decode 在计时外建立历史前缀，每次恢复到相同逻辑长度后只计算一个位置。表中 Decode 长度包含当前 token。未使用 torch.compile、CUDA Graph 或生产级推理调度。

## Dense 与 FlashAttention

| 工作负载 | 逐 head 实现 ms | 合并多头普通实现 ms | 独立 FA2 ms |
| --- | ---: | ---: | ---: |
| Prefill B=1 S=512 | 20.432 | 7.527 | 7.117 |
| Prefill B=1 S=2048 | 20.797 | 8.931 | 7.164 |
| Prefill B=8 S=2048 | 60.868 | 63.508 | 22.468 |
| Decode B=1 KV=512 | 18.542 | 7.151 | 6.918 |

这里有两步不同的优化。长度 512、batch=1 时，从逐 head 改成合并多头，变化远大于之后换成 FA2 的变化；不能把 20.432 到 7.117 ms 都算作 FlashAttention 的收益。

长度 2048、batch=8 时，普通实现需要更大的完整 score/probability 临时张量。FA2 相对合并多头普通实现的 Prefill 耗时约减少到 1/2.83，峰值 allocated 显存由约 2164.8 MiB 降到 791.8 MiB。逐 head 普通实现的峰值约 792.8 MiB，因为它逐 head 分配分数矩阵，不能简单说所有普通实现都具有同样峰值。这个 case 里，单独合并多头甚至没有加速；并行、临时张量和内存流量需要一起看。

Attention 微基准在 B=1、12 heads、head dim=64、S=2048 时，普通合并实现前向约 1.067 ms，独立 FA2 约 0.244 ms。但整模型还包括投影、归一化、RoPE、FFN、缓存和 LM Head，不能把算子级加速比直接当成整模型加速比。

## MLA 的存储与执行代价

三个 MLA 变体参数相同，均为 111,858,432；只改变历史状态的保存方式和投影执行次序。下面用 B=1、KV=2048、BF16、静态缓存与普通 math 后端对比。

| MLA 路径 | 全部层的逻辑缓存 MiB | 单步 Decode ms |
| --- | ---: | ---: |
| 保存展开后的 K/V | 36.00 | 8.495 |
| 保存压缩状态 每步重建 K/V | 3.75 | 8.630 |
| 压缩缓存与矩阵吸收 | 3.75 | 8.987 |

缓存容量缩小了 9.6 倍，延迟却没有同样缩小。这份实现演示的是数学变换，不是 FlashMLA：默认吸收路径的 QK 通道为 160、Value 潜在通道为 128；普通实现还会将共享的历史状态沿 head 维复制成临时张量，以便调用通用矩阵运算。

因此，存得少不代表当前代码实际搬得少，更不代表一定算得快。要获得生产级 MLA 性能，还需要匹配缓存布局和计算路径的专门 kernel。这组数值也不能用来断言 MLA 普遍慢于 MHA，因为模型结构、参数量和实现优化程度不同。

2026-11-01 已补齐另一套与官方 naive/absorb 路径对齐的实现、数值检查和真实语料训练，见 [MLA 补充记录](mla-reference-20261101.md)。新实现不再显式沿 head 复制完整压缩缓存；以上首轮数据保留原样，不与新实现混用。

## MoE 的执行观察

当前 MoE 是 8 个路由专家、Top-2、专家中间维 512，无共享专家；不设容量截断、不丢 token，用逐专家 gather 和 index_add 实现，不是 fused/grouped GEMM。

该配置每个 token 激活的路由专家 FFN 权重数是 Dense FFN 的一半，但在 B=1、KV=2048、math 后端、静态缓存下，MoE Decode 约 14.246 ms，Dense 约 7.310 ms。MoE 总参数也更多，分别约 1.480 亿和 1.197 亿，二者没有做模型质量对齐。

这只能说明当前路径中的路由、动态索引、多个小矩阵与聚合开销值得分析，不能从激活参数或 FLOPs 直接推断延迟。尤其要结合下一节的 BF16 路由敏感性：这些 MoE 计时是执行开销观察，不是低精度等价推理已经完整验证的证明。

## 低精度路由的补充检查

额外使用完整参数规模和固定 33 个随机 token，比较整段前向与 17/1/15 分块前向。FP32 下，6 个模型变体的两种缓存方式均通过，所有相关最大绝对误差在 5e-6 内。此检查使用未训练的随机权重，不是模型质量评估。

BF16 下，Dense 和三个 MLA 路径满足预先设定的容差，但 MoE 和 MLA+MoE 没有全部满足：

| 基线变体 | 完整与分块 logits 最大绝对差 | 使用完整前向专家 ID 重放后的差 |
| --- | ---: | ---: |
| MoE | 0.20239 | 0.03125 |
| MLA+MoE | 1.10742 | 0.04333 |

核对逐层专家 ID 后，确实发现 Top-k 选择变化。最早的变化通常出现在第 k 与第 k+1 个候选概率很接近的位置，之后会沿网络传播。右列只是诊断：借用完整前向的专家 ID，隔离离散路由变化的影响；没有用于性能测试，也不是实际推理可以采用的优化。

另做了 FP32 router 投影对照，也没有保证全部专家选择一致。隐藏状态自身的 BF16 差异仍可传入路由器；在这个随机样本里，FP32 router 甚至不对所有指标都更好。因此保留原有基线精度，新增显式 `router_float32` 实验选项，不把它写成已解决所有问题的修复，也没有放宽检查容差来让结果通过。

这部分说明：线性层的数值误差小，不代表接上 Top-k 后，完整模型的执行路径仍然不变。后续应结合训练后权重、路由边界分布和明确的精度策略继续验证。目前不宣称 BF16 MoE 端到端对齐已全部通过。

## GPU 时间线

在 B=1、KV=512、BF16、静态缓存、3 次 Decode 的 PyTorch Profiler 记录中，实际 kernel 数如下：

| Dense 实现 | 3 次 Decode 的 kernel 数 |
| --- | ---: |
| 逐 head | 3402 |
| 合并多头普通实现 | 1548 |
| 独立 FA2 | 1422 |

这些计数来自 Chrome trace 的 `kernel` 活动，不包含 `gpu_user_annotation` 范围。不能把嵌套的用户标记时间相加成 GPU 工作量，也不能把 kernel 区间覆盖率叫作硬件利用率。

本轮采集了 CUDA kernel、CUDA Runtime、CPU 算子和内存事件，可以分析调用数量与时间线间隙。没有用 Nsight Systems 做额外采集，也没有采集 Nsight Compute 硬件计数器；不能据此给出精确的 SFU、Tensor Core 或 DRAM 瓶颈占比。Profiler 带来的额外开销不用于正式延迟表。

## 训练与未覆盖项

首轮训练步骤计时包含 zero_grad、前向、交叉熵及辅助损失、反向传播和 AdamW 更新。输入是同一批固定随机 token，重复更新会记住这批数据，因此不展示它的 loss 作为语言学习能力证明。后续已为 FA2 和 SDPA Flash 分别补做 Seq-Monkey 真实语料的 300 步训练，配置、曲线与边界见[补充记录](seq-monkey-attention-backends-300.md)；第一篇的原始实验保持原样。

FA3 需要换到 Hopper 环境。FA4 的补充测试见下节，不能将其与首轮不同 PyTorch 版本的结果直接混作后端对照。MLA 使用的是教学数学结构，MoE 是可读的单卡实现，没有复现完整 DeepSeek，也没有测跨卡专家通信。当前结果用于组织第二篇的问题与实验，不直接当作某种芯片架构的性能上限。

## 补充：复用 PyTorch 2.8 验证 FA4

服务器已有 `/root/.venv`，其中是 Python 3.12.3、PyTorch `2.8.0+cu128`，且具备 `torch.float4_e2m1fn_x2`。新建独立的 `.venv-fa4-torch28`，通过 `.pth` 只读复用已有包，额外依赖安装到新环境；没有升级或改写原有 PyTorch 环境。FA4 仍为 `4.0.0b36`，CuTe DSL 为 `4.8.1`。

在这一组合下，FA4 导入成功。BF16、B=1、12 heads、head dim=64、KV 长度 512 的两种 Attention 前向均执行成功：Q 长度分别为 512（Prefill）和 1（单 token Decode）。两者与相同低精度输入提升到 FP64 后的参考实现对比，均通过既定容差，relative L2 误差分别约为 0.00172 和 0.00190。这是算子级前向检查，不是整模型或完整训练验证。

同环境的小规模计时如下，均为同步墙钟中位数，预热 3 次、测量 10 次，包含主机调用开销；仅用来确认执行情况，不作为稳定的性能排名：

| Attention 前向 | math ms | PyTorch SDPA Flash ms | FA4 包 ms |
| --- | ---: | ---: | ---: |
| Q=512 KV=512 | 0.279 | 0.117 | 0.239 |
| Q=1 KV=512 | 0.275 | 0.195 | 0.234 |

包含反向的检查中，6 个 FA4 case 均失败，报错为 `Unsupported compute capability. Supported: 9.x, 10.x, 11.x, 12.x`。核对已安装包的 `flash_attn/cute/interface.py`：前向允许 8.x，并选择 `FlashAttentionForwardSm80`；反向入口的架构检查不接受 SM89。因此，目前的准确结论是：**换用 PyTorch 2.8 解决了导入障碍，4090 上已验证的前向可以运行，但该版本的反向入口仍不支持这张卡。** 不修改架构断言来强行运行，也不将 SM8x 路径代表为 Blackwell 优化内核。

原始记录保存在本地 `runs/rtx4090-20261025/torch28-fa4-check/` 和 `torch28-fa4-forward/`，均含独立环境与参数记录；首轮 PyTorch 2.7 数据未被覆盖。前向编译还有 `AuxData` 参数适配警告，本轮未阻止上述两个前向 case 执行，不据此宣称其他形状或功能也已兼容。
